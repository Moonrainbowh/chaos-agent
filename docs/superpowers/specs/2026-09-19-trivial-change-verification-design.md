# 微小改动分级验证设计

## 目标

在不移除可信完成门的前提下，为单文件、小规模、未命中已知风险信号的修改提供近零成本验证路径。符合条件的修改不启动项目测试或构建进程，由 Host 对完整 diff 作确定性风险判断并记录可审计证据；其余修改继续沿用现有渐进验证与有界修复循环。

## 当前问题

现有验证系统已经区分 `LOW`、`MEDIUM`、`HIGH` 和 `CRITICAL`：纯文档与非可执行资源可以免测试，普通代码运行影响域测试，高风险代码进入完整门禁。但是，边界明确的单文件小改动默认仍属于 `MEDIUM`，会触发项目发现和测试进程。对于文案、样式值、局部常量或其他小范围修改，这些成本可能高于修改本身。

不能通过取消完成门解决这个问题。模型自述“修改很简单”不是可信证据；按用户提示词判断风险也无法覆盖实际 diff。优化点应位于 Host 已经掌握完整变更后的风险规划阶段。

## 已考虑方案

1. **新增 `TRIVIAL` 风险层（选定）。** 风险模型显式表达近零成本路径，Planner、证据账本和界面可以区分“微小代码改动”与“纯文档低风险改动”。
2. **保留 `LOW` 并增加小 diff 跳过原因。** 改动较少，但会混合两种不同信任依据，后续无法独立审计或校准微小改动阈值。
3. **在最终验证服务中按行数短路。** 实现最快，但会绕过统一 Planner，使 milestone 与 final gate 产生不一致决策。

## 选定设计

### 风险层级

`RiskTier` 增加 `TRIVIAL`，完整顺序为：

`TRIVIAL < LOW < MEDIUM < HIGH < CRITICAL`

`TRIVIAL` 表示 Host 已对一个完整、可分析的单文件小 diff 完成风险筛查，并确认无需启动项目测试进程。它不表示“没有验证”，也不允许模型自行声明。

现有 `LOW` 语义保持不变，继续表示纯文档或明确的非可执行资源。现有 `MEDIUM`、`HIGH` 和 `CRITICAL` 的测试与构建策略不变。

### 微小改动候选

一个修改只有同时满足以下条件，才进入 `TRIVIAL` 候选：

- 仅修改一个文件；
- unified diff 正文完整且非空；
- 新增行与删除行总数不超过 20 行；
- 计数排除 `+++`、`---` 文件头，但包含空白、注释和正文行，避免通过行类型规避阈值；
- diff 不是二进制、生成摘要或截断正文；
- 路径规则未将文件判为 `HIGH` 或 `CRITICAL`。

20 行是首版内部常量，不增加用户配置。后续只能依据真实任务完成率、误判率和验证耗时数据调整。

### 强制升级信号

候选 diff 命中以下任一信号时，不得成为 `TRIVIAL`，并至少保持现有路径风险或升级到对应风险层：

- 函数、方法或类签名，公开导入导出，类继承关系；
- 认证、授权、权限、凭据、密钥、加密或路径安全；
- 数据库、迁移、schema、序列化、持久化或恢复逻辑；
- 并发、锁、异步任务、线程、进程、网络、协议或状态机；
- 控制流和异常处理，包括条件、循环、匹配、抛出与捕获；
- 依赖清单、构建、发布、CI、运行入口和配置文件；
- 测试文件、快照、fixture、生成文件或 vendored 文件；
- 位运算，以及现有补丁风险规则已识别的高风险语义；
- 无法可靠解析、正文缺失或带 `PATCH_BODY_TRUNCATED` 的 diff。

这些规则是保守风险线索，不尝试证明行为等价。未命中规则只允许省略项目测试，不允许扩大权限、跳过写后安全检查或伪造运行结果。

### 规划与执行

风险决策顺序如下：

1. 路径与语义图先建立风险下界；`HIGH`、`CRITICAL` 不得被小 diff 降级。
2. Patch 分类检查完整性、行数和强制升级信号。
3. 仅当路径下界允许且 patch 满足全部候选条件时，结果设为 `TRIVIAL`。
4. `VerificationPlanner` 为 `TRIVIAL` 生成 `skip_tests=true`、`require_full_gate=false` 的计划。
5. 支持现有 L0 语法检查的 Python、JSON 和 TOML 文件仍执行确定性快速检查；语法失败沿用现有阻断与修复路径。
6. Milestone 和 final gate 对同一 generation、subject 和完整 diff 得出同一风险层，不启动项目发现、测试或构建进程。

Planner 的原因中必须记录单文件、实际变更行数、20 行阈值以及未命中强制升级规则的稳定结论。不能保存整段 diff 或模型正文。

### 完成证据

`TRIVIAL` 通过后，由系统 Planner 为当前 generation 和 subject 写入 `SYSTEM_PLANNER` evidence，满足风险验证条件。该证据只能由 Host 基于 `VerificationPlan` 生成。

现有纯文档免测试继续使用相同 provenance，但保留独立原因。免测试判定必须同时支持：

- 路径明确为文档的 `LOW` 计划；
- 完整 diff 经风险筛查后的 `TRIVIAL` 计划。

不能仅凭扩展名、文件数量、模型工具参数或用户声称“简单修改”生成 `TRIVIAL` 证据。无 diff、截断 diff 和状态恢复后缺失 diff 的任务必须回到保守验证，不得沿用旧 attestation。

### 修复循环

`TRIVIAL` 不主动启动项目测试，因此正常情况下不会产生测试失败后的额外模型修复回合。若 L0 语法检查失败，任务仍进入现有修复循环；修复后的新 generation 必须重新分类，不能复用上一 generation 的风险证明。

`MEDIUM`、`HIGH` 和 `CRITICAL` 的验证失败、最多三次 repair cycle、重复失败保护和用户决策状态均保持不变。

## 组件边界

- **Verification risk**：定义 `TRIVIAL`、20 行候选规则、强制升级信号和稳定原因。
- **Verification Planner**：将风险层映射为语法目标、测试选择、完整门禁和免测试计划。
- **Verification evidence/service**：只依据 Host 计划记录当前 generation/subject 的免测试证据，并避免进入项目发现。
- **Core**：保持现有完成门和修复状态机，不增加基于模型正文的快捷路径。
- **Interfaces、Policy、Runtime 和 Providers**：行为不变；不新增用户模式，不改变工具权限，也不把免测试描述为已运行测试。

## 失败行为

- diff 为空、不完整、截断、二进制或超出分析上限时，失败闭合到现有保守风险层。
- 路径风险与 patch 风险冲突时取更高风险，唯有完整且符合规则的单文件小 diff 可以从普通 `MEDIUM` 下调为 `TRIVIAL`。
- 任何语法错误都阻止 attestation，并保留实际写入后的任务状态供修复。
- generation、subject 或 diff 变化后，旧 `TRIVIAL` evidence 不得满足新的完成条件。
- 项目发现或测试工具不可用不影响已经确定的 `TRIVIAL` 计划，因为该路径不应启动这些步骤。

## 验证计划

- 对 1 行、20 行、21 行以及双文件修改测试非对称阈值边界。
- 验证删除行与新增行共同计数，文件头不计数，空白和注释仍计数。
- 验证普通单文件小逻辑 diff 成为 `TRIVIAL`，且 milestone/final plan 均跳过测试和完整门禁。
- 分别用函数签名、控制流、导入导出、安全、持久化、并发、网络、配置、测试文件和截断 diff 证明强制升级。
- 验证现有 `HIGH/CRITICAL` 路径不会因改动少于 20 行而降级。
- 验证 Python/JSON/TOML 的 L0 语法错误仍阻断并进入修复路径。
- 验证 `TRIVIAL` 产生绑定当前 generation/subject 的 `SYSTEM_PLANNER` evidence，并且不创建项目测试调用。
- 验证新 generation 不能复用旧 attestation。
- 保留文档 `LOW`、普通代码 `MEDIUM`、高风险完整测试和关键风险 tests→build 顺序的现有回归。

## 验收标准

- 单文件、完整、总变更不超过 20 行且未命中风险信号的修改，不启动项目测试或构建进程即可通过可信完成门。
- 任一强制升级信号、21 行改动或第二个文件都会恢复现有验证强度。
- 终端与持久记录能区分 `TRIVIAL` 免测试证明和实际 verifier PASS，不宣称运行了未运行的测试。
- 现有权限、安全、预算、修复次数和高风险验证行为不发生弱化。

## 非目标

- 提供全局 `--no-verify` 或允许模型自行跳过验证。
- 证明小 diff 的行为等价或无回归。
- 修改用户交互模式、模型选择或 Planner/Executor 拓扑。
- 为首版增加可配置阈值或按仓库保存例外规则。
- 降低现有安全、持久化、依赖、入口和核心子系统的风险等级。
