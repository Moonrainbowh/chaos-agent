# Chaos Agent 1.0.2 安全可靠性收口与 1.1.0 可信自主执行规划

## 状态

- 规划日期：2026-07-13
- 当前状态：已确认方向，尚未按本计划开始实现
- 执行顺序：必须先完成并发布 `1.0.2`，再进入 `1.1.0`
- 产品基线：Windows-first、前台单任务、Claude Code 风格单栏终端、中文 Windows 默认中文

## 总目标

把 Chaos Agent 从“能够在已授权工作区持续修改、测试、暂停和恢复”，推进到“只能在权限边界内执行，并且只有拿到与任务目标对应的验证证据后才能宣布完成”。

两个版本承担不同职责：

| 版本 | 定位 | 核心问题 |
| --- | --- | --- |
| `1.0.2` | 安全可靠性收口 | 修复当前命令授权、TUI 单任务、退出恢复、语言切换、持久预算和 Windows 运行时回归 |
| `1.1.0` | 可信自主执行 | 建立验收条件、强制验证状态机、证据账本、结构化修复循环和真实任务评测体系 |

## 已锁定的产品决策

- 工程请求继续默认创建前台自主任务。
- 工作区内 typed 读取和编辑继续由任务授权自动允许。
- 原始 PowerShell 脚本不再因为存在任务授权而自动执行。
- 无提示测试、构建和 lint 由受信的结构化验证器提供，不由模型拼接任意 shell 文本。
- 本机 Runtime 仍不是操作系统级沙箱；不得宣称能够约束被执行项目代码的所有文件和网络行为。
- 同一 TUI 同一时刻只允许一个前台任务运行；运行中普通输入一律作为 steering。
- `Esc` 暂停任务；关闭 TUI 产生可恢复的 `INTERRUPTED`，不转入后台。
- 从 `1.1.0` 起，`COMPLETED` 必须由系统验证门槛产生，模型文字不能直接决定完成；`1.0.2` 只提供安全验证入口，不宣称已经实现可信完成。
- 中文 Windows 默认中文，允许在 TUI 中切换英文；代码、路径、命令和原始工具数据不翻译。
- 本阶段不实现 daemon、手机观察、云端执行、多任务并发、自动 worktree、自动 commit、自动 push 或 MCP 动作调用。

# 版本 1.0.2：安全可靠性收口

## 1.0.2 发布目标

在不扩大功能面的前提下，恢复前台单任务语义，堵住原始命令自动授权漏洞，使恢复预算在下一次外部动作前生效，并让 Windows Runtime、全量测试和真实终端验收全部通过。

`1.0.2` 的 typed verification 只解决“如何安全地自动运行常用本地检查”，不改变最终完成裁决，也不把当前任务状态宣传为 evidence-backed completion；强制证据门槛属于 `1.1.0`。

## 1.0.2 范围

### 1.0.2 包含

- 原始 PowerShell 降权与结构化验证入口。
- TUI 单前台任务、steering、暂停、关闭中断和恢复。
- 中文默认与英文切换真正接入渲染。
- 持久预算字段保真和模型调用前预算闸门。
- Windows 进程树超时回归诊断与稳定修复。
- 构建元数据弃用警告的低风险修正。
- 完整自动测试、wheel 安装 smoke 和 Windows Terminal 人工验收。

### 1.0.2 不包含

- 通用 verifier registry、复杂验收条件和完整证据账本。
- Node、.NET、Rust 等多工具链自动发现。
- MCP 工具执行、远程服务、daemon、多任务并发。
- 自动 worktree、commit、push 或自动回滚用户原有改动。

## 1.0.2 目标行为

### 命令授权

Policy 必须区分两个内部能力：

```text
RAW_SHELL     模型提供任意 PowerShell 文本
VERIFICATION  模型只选择本地注册的受信验证 kind
PROTECTED_PATH typed 文件请求命中明确保护清单
```

- `run_command` 分类为 `EXECUTE + RAW_SHELL`。
- `run_verification` 分类为 `EXECUTE + VERIFICATION`。
- 任务授权只允许 root 匹配、显式允许本地执行的 `VERIFICATION`。
- `RAW_SHELL` 在所有任务授权下仍为 `ASK`，critical shell 仍为 `DENY`。
- `PROTECTED_PATH` 至少覆盖现有 `.git`、`.chaos-agent`、`.code-agent`、`.env` 和私钥名称规则；任务授权不能自动放行。这里不宣称能够自动识别所有可能包含秘密的文件。
- 非交互模式使用稳定的 `error_code=approval_required`，core 不再匹配英文错误文本。

| 动作 | 任务授权下行为 |
| --- | --- |
| `read_file`、`list_files`、`search_text` | 工作区内自动允许 |
| `write_file`、`replace_text` | 工作区内自动允许 |
| 受信结构化验证 | 自动允许，命令由本地 adapter 生成 |
| 任意 `run_command` PowerShell | 必须询问，不因任务授权自动放行 |
| 网络、外部路径、明确 protected path、critical 动作 | 拒绝或等待明确决策 |
| 未知工具 | 拒绝 |

唯一公开 schema 建议为：

```text
run_verification(kind, cwd, targets, timeout_s)
```

模型不得提供 `executable`、`argv`、`command`、`env` 或 URL。结构化验证首版只覆盖当前最需要的 Python 路径：

- `python_unittest`
- `pytest`
- `python_compileall`
- `python_build`

验证请求只能携带受限的相对 `cwd`、受限 targets 和 timeout；不能携带任意脚本文本、环境变量、URL、shell 运算符或安装参数。adapter 负责使用 `sys.executable -m ...` 生成 argv，并且不执行依赖安装、restore、download 或 package update。`python_build` 固定使用 `python -m build --no-isolation`；缺少本地构建依赖时返回结构化 unavailable，绝不回退 raw shell。

typed verifier 消除的是“模型任意 shell 自动授权”，不是操作系统沙箱。被验证的工作区项目代码仍可能在当前 Windows 用户权限下访问网络或工作区外资源，因此只允许在用户已授权、被视为可信的工作区运行，并在 README/TUI 中明确这一点。

### TUI 审批

- 审批界面显示经过终端控制字符净化的完整命令、cwd、risk 和 policy reason。
- 批准只对当前一次请求生效，不记忆为全局规则。
- 只有 `y` 明确批准；`n`、`Esc`、空 Enter 和关闭 TUI 均拒绝。
- 审批挂起时禁止提交第二任务或第二条普通输入。
- 关闭或 `Ctrl+C` 必须先取消审批，并断言 Runtime 调用次数为 0。
- 命令与路径可以作为有界审计信息持久化；被拒绝命令关联的 fixture secret 内容不得进入数据库。

### TUI 生命周期

```text
空闲 --提交工程请求--> RUNNING
RUNNING --普通输入--> steering queue
RUNNING --Esc--> PAUSED + checkpoint
RUNNING --关闭 TUI--> INTERRUPTED + checkpoint
PAUSED/INTERRUPTED --显式继续--> RUNNING
RUNNING --停止--> FAILED(user stopped)
```

- TUI 不再为前台任务维护第二套无效 cancellation token。
- 新任务启动前必须确认没有仍在运行的前台任务。
- steering 在安全边界消费，并且不会在恢复时重复播放。
- TUI 关闭必须先请求 controller 中断并等待持久状态完成，再取消 UI 辅助协程。
- Windows Terminal 强制关闭标签页或进程可能来不及执行 finally；每次任务运行必须记录 execution instance、PID 和 create_time。应用启动时只对账确认 owner 进程身份已失效的 `RUNNING`/`VERIFYING` 任务，原子转为 `INTERRUPTED`、创建 checkpoint，并确保不重放在途命令；仍由活进程持有的任务不得被第二个实例误中断。

# 版本 1.1.0：可信自主执行

## 1.1.0 发布目标

让 Agent 在没有逐步人工监督的情况下，能够自行明确验收条件、选择可信验证器、执行有界修复循环，并且只有在最新代码状态满足必需证据时才宣布完成。

## 1.1.0 成功定义

一个代码修改任务只有同时满足以下条件才能进入 `COMPLETED`：

1. 已存在结构化任务目标和验收条件。
2. 每个必需验收条件都有当前代码代次对应的证据。
3. 最近一次修改之后至少执行过一次适用验证。
4. 没有未解决的必需验证失败。
5. 没有未处理的权限决策、开放问题或预算暂停。
6. 最终结果明确列出改动、证据、未验证项和剩余风险。

模型输出“完成了”不属于验证证据。

## 1.1.0 范围

### 1.1.0 包含

- 结构化验收条件和任务类型。
- 真正使用 `VERIFYING` 的完成状态机。
- 持久 evidence ledger 和代码代次关联。
- verifier registry 与 Windows 项目工具链发现。
- Python、Node 和 .NET 的首批本地验证 adapter。
- 基于结构化失败的有界修复循环。
- 单栏终端中的证据化交付摘要。
- 可回放任务场景、确定性 grader 和真实模型 benchmark。

### 1.1.0 不包含

- 用第二个模型替代确定性验证器做最终裁决。
- 让 model-authored self-review 成为完成证据。
- 自动安装依赖、联网 restore 或 package update。
- daemon、远程观察、多任务并发或云端执行。
- 默认 worktree、自动 commit 或 push。
- MCP 动作桥接和第三方可执行 Skill。

## 1.1.0 核心模型

### 任务意图

```text
READ_ONLY    只回答、读取或分析，不修改工作区
MODIFY       修改工作区，必须验证最新 subject
AUTO         由 system 根据实际写入升级为 MODIFY
```

### 验收条件

建议值对象：

```python
AcceptanceCriterion(
    id: str,
    label: str,
    verifier_id: str | None,
    params: Mapping[str, JSONValue],
    source: CriterionSource,       # system | user | project | agent
    strength: CriterionStrength,   # authoritative | independent | self_authored | integrity
    requirement: CriterionRequirement,  # required | advisory
)
```

约束：

- 用户明确条件优先级最高，Agent 不能删除或降级。
- system 为 `MODIFY` 任务自动添加“最新修改后完成验证”和“无未解决必需失败”。
- Agent 可以提出额外条件，但只能从已注册 verifier 中选择。
- 纯手工条件必须标为 `UNAVAILABLE` 或等待用户确认，不能伪造通过。
- 项目既有测试、构建和 lint 属于 `INDEPENDENT`；用户明确 oracle 属于 `AUTHORITATIVE`。
- Agent 新增测试属于 `SELF_AUTHORED`，只有记录 red-green 过程或同时存在独立证据时，才能作为行为修改的主要依据。
- `git diff --check`、语法检查和文件存在性属于 `INTEGRITY`，不能单独证明 Bug 已修复。
- 首次成功写入后，既有 required criterion 不可削弱，只能追加；用户 steering 可显式创建新的 contract revision。
- 修改型任务缺少可信 required criterion 时可以继续探索，但不能进入 verified completion。

### 证据记录

```python
EvidenceRecord(
    criterion_id: str,
    verifier_id: str,
    outcome: VerificationOutcome,
    code_generation: int,
    subject_hash: str,
    command_summary: str,
    exit_code: int | None,
    bounded_diagnostic: str | None,
    output_sha256: str | None,
    truncated: bool,
    provenance: EvidenceProvenance,
    started_at: datetime,
    finished_at: datetime,
)
```

`VerificationOutcome`：

- `PASSED`
- `FAILED`
- `ERROR`
- `UNAVAILABLE`
- `UNSTABLE`
- `SKIPPED_BY_USER`

`SKIPPED_BY_USER` 永远不能满足 required criterion。人工确认使用独立 `USER_CONFIRMED` provenance，并且只允许满足明确声明为手工验收的用户 criterion，不能替代项目测试或系统完整性条件。

证据只追加，不覆盖；不得保存 API key、环境变量值、完整源文件、完整 prompt 或无界命令输出。完整输出只保存 hash、截断标记和有界脱敏摘要。

### 代码代次

- workspace typed 写入结果返回结构化 `ActionEffect` 和 subject snapshot/hash。
- core 是 generation 推进规则的唯一所有者；它根据成功 `ActionEffect` 请求 sessions 原子执行 `code_generation += 1` 并失效旧证据。
- sessions 负责原子持久化，不在 `code_agent_win` 中实现 generation 业务规则。
- 证据必须绑定生成时的 `code_generation`。
- 新写入自动使旧代次通过证据失效。
- 只读动作不改变代次。
- checkpoint 保存当前代次、验收条件和证据摘要。

## 1.1.0 状态机

```text
CREATED
  -> RUNNING
  -> VERIFYING
      -> COMPLETED          所有必需条件通过
      -> RUNNING            验证失败且仍有修复预算
      -> WAITING_DECISION   需要用户条件、权限或手工验收
      -> PAUSED             预算、卡滞或环境不可用
      -> FAILED             不可恢复错误或用户停止
      -> ACCEPTED_PARTIAL   用户明确接受未完全验证的部分交付
```

完成规则：

- 模型无工具调用时，内核执行 completion assessment，而不是直接完成。
- `MODIFY` 任务缺少最新代次验证时自动进入 `VERIFYING`。
- 验证失败回到 `RUNNING`，并把结构化失败证据加入下一轮上下文。
- 验证不可用时进入 `WAITING_DECISION` 或 `PAUSED`，不得伪装成功。
- 删除通用 `RUNNING -> COMPLETED`；模型无工具调用只提交 completion candidate。
- `transition_task(..., COMPLETED)` 不再是通用 API；sessions 提供原子 `finalize_task(task_id, verification_run_id)`，复核最新 contract revision、required evidence 和 subject hash。
- 用户可以显式接受部分验证，但终态必须是 `ACCEPTED_PARTIAL`，不得改写为 `COMPLETED` 或系统验证通过。
- `ACCEPTED_PARTIAL` 只能由显式用户决定产生，是 terminal 但不计入 verified success rate，也不能被 Agent 自动选择。

## 1.1.0 Feature 划分

| --- | --- | --- |

| `verification` | verifier registry、runner、证据模型、结果归一化、失败分类和稳定指纹 | 调用模型或直接决定任务状态 |

首批场景至少覆盖：

### Task 18：实现 Projects Discovery

首批支持：

| 生态 | 发现信号 | 可信候选 |
| --- | --- | --- |
| Python | `pyproject.toml`、`pytest.ini`、`tox.ini`、测试目录 | unittest、pytest、compileall、build |

- [ ] 只读扫描清单和本机 executable 可用性。

### Task 19：扩展 Verifier Registry

- [ ] verifier 根据受信 adapter 生成 argv，不接受模型提供的完整命令。
- [ ] 每个 verifier 声明适用生态、验证范围、timeout 和预计成本。
- [ ] 统一归一化 exit code、stdout/stderr 摘要和失败指纹。
- [ ] 输出绑定当前 code generation 的 evidence。
- [ ] 用户批准的自定义命令单独标记 provenance，不伪装成系统 verifier。
- [ ] 新验证执行仍使用净化环境和 cancellation-safe runtime。
- [ ] 失败指纹使用规范化 JSON 的 SHA-256，排除时间、随机值、临时路径和原始秘密。
- [ ] 删除“所有失败 `run_command` 都算验证”的路径；只有 registry 产生的 `VerificationEvidence` 才进入验证/修复统计。
- [ ] 验证失败生成结构化 `RepairDirective`；工具/依赖缺失和 verifier 内部错误不进入代码修复循环。
- [ ] 相同 subject 下相同失败直接视为无进展；失败后无修改却突然通过时标为 `UNSTABLE` 并要求确认运行。
- [ ] 验证运行次数、命令数和耗时使用独立持久预算。

退出门槛：Python、Node、.NET 各至少一个测试 verifier 和一个 build/lint verifier 通过 Feature 测试。

### Task 20：实现强制 VERIFYING 状态机

- [ ] 模型停止调用工具时调用 completion assessment。
- [ ] `MODIFY` 任务缺少有效证据时进入 `VERIFYING`。
- [ ] verifier 失败后回到 `RUNNING`，并消费一个 repair cycle。
- [ ] verifier unavailable 时进入 `WAITING_DECISION` 或 `PAUSED`。
- [ ] core 根据 `ActionEffect` 请求 sessions 原子推进 generation 并失效旧证据。
- [ ] 恢复 `VERIFYING` 任务不重放在途 verifier，而是重新评估当前状态。
- [ ] 所有状态转换先持久化，再发布 UI 事件。
- [ ] 模型 completion candidate 不能直接调用通用 completed transition。

必须新增的负向测试：

- 模型直接说完成但从未验证 -> 不得 `COMPLETED`。
- 测试通过后再次写文件 -> 旧证据不得完成任务。
- 必需测试失败但模型停止 -> 返回修复或暂停，不得完成。
- verifier 缺失 -> 明确 unavailable，不得伪造通过。
- 重启时预算已耗尽 -> 零 provider/verifier 调用。
- 用户接受部分交付 -> `ACCEPTED_PARTIAL`，不得 `COMPLETED`。

退出门槛：`TaskStatus.VERIFYING` 在成功、失败、不可用和恢复路径均有真实覆盖。

- [ ] generation 增加、旧证据失效和 ActionEffect 持久化保持事务一致。
- [ ] evidence 摘要有严格大小和字段白名单。
- [ ] 恢复后 completion assessment 与进程退出前一致。
- [ ] `finalize_task` 在单事务中复核 `VERIFYING`、最新 revision、全部 required PASS 和 subject hash 未变化。
- [ ] 未结束 verification run 在恢复时先标为 `INTERRUPTED`，不能复用为成功证据。

退出门槛：从 1.0.2 数据库升级无数据丢失；重开数据库后证据与完成判断一致。

# 后续方向

只有在 1.1.0 证明“安全越界为 0、假完成为 0、成功率可测”之后，才评估：

1. 用户确认后的本地 commit 交付。
2. 可选 worktree 隔离模式。
3. 更多工具链和 LSP/编译器诊断。
4. policy-gated MCP 动作桥接。
5. 多 Agent 分工或后台执行。

这些能力都不能绕过同一套 task contract、verification evidence 和 policy boundary。

# 最终完成定义

本双版本规划完成时，Chaos Agent 应满足：

- 在已授权工作区内能默认自主编辑、执行受信验证、失败后有界修复。
- Agent 直接请求的 raw PowerShell、网络、外部路径、明确 protected path 和 critical 动作不能因任务授权静默放行。
- typed verifier 执行的已授权项目代码仍运行在当前 Windows 用户权限下；其间接文件和网络副作用不受 OS 级隔离保证，产品必须持续如实提示这一残余边界。
- 终端始终只有一个前台任务，关闭后不后台运行，但可安全恢复。
- 中文 Windows 默认中文，英文切换真实生效。
- 恢复后的所有预算和卡滞状态在下一次模型或工具动作前生效。
- 修改任务只有在最新代码代次满足必需验收证据时才能标记完成。
- 最终回答能够被用户和自动 grader 从工作区、命令结果和持久 evidence 中独立复核。
