# 搜索时间预算：先放宽上限定位截断原因

固定查询 `def _literal_columns`，全仓库范围；仅更改实例的 `search_timeout_s`，不改产品默认值。2、5、10、20 秒各三次，交替顺序；随后补充一次 60 秒试验。未控制 OS 缓存；60 秒试验时新增了前面试验的诊断 JSON。

| 时间预算 | 完整返回 | 实际耗时 |
|---|---:|---:|
| 2 秒 | 0/3 | 约 2 秒 |
| 5 秒 | 0/3 | 约 5 秒 |
| 10 秒 | 0/3 | 约 10 秒 |
| 20 秒 | 0/3 | 约 20 秒 |
| 60 秒 | 0/1 | 59.987 秒 |

60 秒试验已尝试读取 9414 个文件，最后访问 `.venv-regression/final-install/Lib/site-packages/pip/_vendor/cachecontrol/adapter.py`。三条命中均为该回归环境中安装的代码副本，尚未到达工作区的目标源码。

`git check-ignore -v` 确认这些文件被 `.venv-regression/.gitignore` 的 `*` 规则忽略。Workspace 的 IgnoreRules 仅加载根 `.gitignore`，未采用该子目录规则，因此扫描纳入了 Git 已忽略的安装环境。

结论：先放宽时间是有效且简单的诊断步骤。本例不仅存在 2 秒预算截断，还暴露了搜索文件范围与 Git 忽略规则不一致。下一步应先对齐文件范围，再测完整耗时，之后才决定默认预算和是否需要性能优化。不能从这次结果得出正确范围内的全仓库搜索本身需要 60 秒。
